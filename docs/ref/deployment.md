# Deployment

## Overview

This guide explains how to deploy Wazuh using Ansible with the `wazuh-ansible` tool. This open-source tool facilitates the automated deployment of Wazuh across various operating systems and architectures ([Compatibility](introduction/compatibility.md)).

Before proceeding, configure your Ansible inventory file (`inventory.ini`) based on the deployment type you intend to perform. For more details on inventory configuration, refer to the [Configuration files](configuration/configuration-files.md) section.

Additionally, ensure you clone the `wazuh-ansible` repository and install the necessary dependencies:

```bash
  git clone --branch v5.0.1 https://github.com/wazuh/wazuh-ansible.git
  cd wazuh-ansible
  ansible-galaxy install -r requirements.yml
```

In a distributed deployment, the deployment playbooks create the passwords and the certificate authority of the deployment on the control node, with `openssl`, as the user running `ansible-playbook`. See [Credentials and certificates](#credentials-and-certificates).

## Deployment Types

Wazuh can be deployed in two primary ways, each tailored to different needs and scales:

- **All-in-One (AIO):** Installs all components on a single node, suitable for small environments or testing purposes.
- **Distributed:** Distributes components across multiple nodes, ideal for larger environments requiring scalability and redundancy.

Additionally, Wazuh Agents can be installed on one or multiple hosts, simplifying security management in diverse environments.

### All-in-One (AIO) Deployment

In an AIO deployment, all components are installed on a single node, including:

- Wazuh Indexer
- Wazuh Manager
- Wazuh Dashboard

To perform an AIO deployment, use the `wazuh-aio.yml` playbook. This playbook installs and configures all required components on one node.

```bash
  ansible-playbook -i inventory.ini wazuh-aio.yml
```

### Distributed Deployment

A distributed deployment spreads components across multiple nodes for improved scalability and redundancy. The components include:

- Three Wazuh Indexer nodes
- Two Wazuh Manager nodes (master and worker)
- One Wazuh Dashboard node

To execute a distributed deployment, use the `wazuh-distributed.yml` playbook, which installs and configures all necessary components across multiple nodes.

```bash
  ansible-playbook -i inventory.ini wazuh-distributed.yml
```

### Wazuh Agent Deployment

For installing Wazuh Agents on one or more hosts, use the `wazuh-agent.yml` playbook. This playbook installs and configures the Wazuh Agent on specified nodes in the inventory.

```bash
  ansible-playbook -i inventory.ini wazuh-agent.yml
```

## Package signatures

The roles download the Wazuh packages from the URLs in `roles/vars/artifact_urls.yaml` and check, on each host, that every package is signed with the Wazuh GPG key before installing it. The key is downloaded from `wazuh_gpg_key_url` and only trusted if its fingerprint is in `wazuh_gpg_key_fingerprints`. The Windows and macOS agent packages are checked with their platform signature instead: the `.msi` must have a valid Authenticode signature from `wazuh_windows_signer_name`, and the `.pkg` must be signed with the Developer ID Installer certificate of the team `wazuh_macos_signer_team_id`. An unsigned or modified package, or a package signed with another key or certificate, stops the deployment before it is installed.

Development packages are not signed. To install them, set `wazuh_skip_package_signature_check` to `true`, for example with `--extra-vars wazuh_skip_package_signature_check=true`. A warning is printed for each package installed without the check. See [Variables](variables.md#package-urls).

## Credentials and certificates

The Wazuh Indexer, Wazuh Manager, and Wazuh Dashboard packages set up their own credentials and certificates when they are installed. Each package keeps them in its own configuration directory (`/etc/wazuh-indexer`, `/etc/wazuh-manager`, `/etc/wazuh-dashboard`):

- `local.env`: the values you supply, such as passwords and the names its certificates must carry.
- `ca/`: the certificate authority (CA) the package issues its certificates from.
- `export/`: what it publishes for the other components on the same host, such as the passwords of the accounts it owns and its CA certificate.
- `certs/<component>-ca.pem`: the CA of each other component it connects to.

What the deployment playbooks provide depends on the deployment type:

| | All-in-One (`wazuh-aio.yml`) | Distributed (`wazuh-distributed.yml`) |
|---|---|---|
| Passwords | Generated by the packages, except those you supply. Read back from each package's `export/credentials.env` and kept in `deployment-credentials/`. | Generated once on the control node, kept in `deployment-credentials/`, and written to each host's `local.env`. |
| CA | Each package mints its own; the others import it from its `export/` on the same host. | One CA for the whole deployment, created once on the control node. Its private key never leaves the control node: the hosts receive only its certificate. |
| Certificates | Issued by each package, with the names in `local.env`. | Issued on the control node from the CA of the deployment, and staged on each host before its package is installed. The packages use them and issue nothing. |

> **Before you start:** the passwords, and in a distributed deployment the CA with its private key and the certificates issued from it, are kept on the control node, in `deployment-credentials/` and `deployment-config-files/wazuh-ca/` (files `0600` in `0700` directories). Protect those directories, or supply the passwords from Ansible Vault with `wazuh_credentials_overrides`.

### Passwords

| Key | Account | Hosts that read it |
|-----|---------|--------------------|
| `WAZUH_INDEXER_ADMIN_PASSWORD` | `admin` (Wazuh Indexer; Wazuh Dashboard login) | Wazuh Indexer |
| `WAZUH_INDEXER_KIBANASERVER_PASSWORD` | `kibanaserver` (Wazuh Indexer) | Wazuh Indexer, Wazuh Dashboard |
| `WAZUH_INDEXER_MANAGER_PASSWORD` | `wazuh-manager` (Wazuh Indexer) | Wazuh Indexer, Wazuh Manager |
| `WAZUH_MANAGER_API_PASSWORD` | `wazuh` (Wazuh server API) | Wazuh Manager |
| `WAZUH_MANAGER_WUI_PASSWORD` | `wazuh-internal-client` (Wazuh server API; used by the Wazuh Dashboard, not a login account) | Wazuh Manager, Wazuh Dashboard |

- On the control node, they are kept in `deployment-credentials/`, next to the playbook, one file per key. Every later run reuses them.
- Before each package is installed, the keys its component reads that already have a value are written to `/etc/<package>/local.env` (`root:root`, `0600`), with the names its certificates must carry. In a distributed deployment that is every key; in an All-in-One deployment, the ones you supplied and the ones a component installed earlier on the host already published. The playbooks do not write the file again once the package is in place.
- Once installed, each package publishes the passwords of the accounts it owns in `/etc/<package>/export/credentials.env` (readable by root only). The health checks of the playbooks use those values. In an All-in-One deployment they are also copied to `deployment-credentials/`; in a distributed deployment, a value that differs from `deployment-credentials/` prints a warning that names the key, never the value.
- To supply your own values, for example from Ansible Vault, set `wazuh_credentials_overrides`. They must follow the password policy of the packages. See [Variables](variables.md#wazuh-credentials).

No task prints a password.

### Certificates

Every certificate carries the names the playbooks set for it: `WAZUH_INDEXER_CERT_SANS`, `WAZUH_MANAGER_REMOTED_CERT_SANS` (agent listener), `WAZUH_MANAGER_APID_CERT_SANS` (Wazuh server API) and `WAZUH_DASHBOARD_CERT_SANS`, plus `localhost`, `127.0.0.1` and `::1`. See [Certificate names](roles/wazuh-manager.md#certificate-names) for the Wazuh Manager.

**All-in-One.** The playbooks stage no CA: each package mints its own CA, and the Wazuh Manager and Wazuh Dashboard packages import the Wazuh Indexer CA, the Wazuh Manager CA, and the client pair of the Wazuh Manager from the `export/` directories on the host.

**Distributed.** As the installation assistant does it: the playbooks create one CA for the whole deployment, once, on the control node, in `deployment-config-files/wazuh-ca/` (`root-ca.pem` and its private key, `root-ca.key`), and issue every certificate there. The private key never leaves the control node. Before each package is installed, each host receives:

| Component | `ca/` | `certs/` |
|-----------|-------|----------|
| Wazuh Indexer | `root-ca.pem` | `indexer.pem` / `indexer-key.pem` (the node) and `admin.pem` / `admin-key.pem` |
| Wazuh Manager | `root-ca.pem` | `remoted.pem` / `remoted-key.pem` (agent listener), `apid.pem` / `apid-key.pem` (Wazuh server API), `root-ca.pem` (the CA served to agents), `indexer-ca.pem`, and `indexer-connector.pem` / `indexer-connector-key.pem` (its own client certificate for the Wazuh Indexer, with the node name as CN) |
| Wazuh Dashboard | — | `dashboard.pem` / `dashboard-key.pem`, `indexer-ca.pem` and `manager-ca.pem` |

With the CA certificate and no key in `ca/`, the packages use these certificates and issue none. The Wazuh Indexer and Wazuh Dashboard packages give the files in `certs/` the group of their service account when they are installed. After the Wazuh Manager package is installed, the playbooks give `certs/` to `root:wazuh-manager` (`0750`, files `0640`) and run its credential resolver again (`wazuh-manager-resolve-credentials --upgrade`), which issues nothing. The step is not required: on RPM systems the package checks the staged files before it gives them its group (it prints `UNSAFE … group is root, not wazuh-manager`), fixes their owner at the end of its installation, and resolves the rest when it first starts. Running the resolver again completes that resolution when the package is installed instead.

The certificates are RSA 2048, SHA-256, valid ten years, and valid from the day before they are issued, so a host whose clock is behind the control node accepts them. The pairs of each host are kept in `deployment-config-files/wazuh-ca/issued/<inventory host>/`. Set `wazuh_manager_indexer_client_certificate` to `false` to skip the client certificate of the Wazuh Manager.

To use your own CA, place its `root-ca.pem` and `root-ca.key` in `deployment-config-files/wazuh-ca/` before the first run. The playbooks only create a CA that is not there.

Each package refuses to start when its credentials or its trust material are missing, invalid, or unsafe, and names the file or the value to fix (`MISSING`, `INVALID`, `UNSAFE`). The playbooks check that each service started, and show those lines when it did not.

### What to keep

`deployment-credentials/` and `deployment-config-files/` belong to the deployment: they hold its passwords and, in a distributed deployment, its CA, the CA private key, and the certificates issued from it. Back them up and do not commit them: they are in `.gitignore`.

### Running a playbook again

Running the same playbook again, from the same directory, keeps the passwords, the CA, and the certificates. The packages do not create their credentials again.

In a distributed deployment, a host whose component already holds the CA of another deployment is refused before anything is written. This happens, for example, when the playbook runs from another directory, or after `deployment-config-files/` was removed. To deploy again from scratch, use new hosts, or first uninstall the Wazuh packages from the hosts and remove `/etc/wazuh-indexer`, `/etc/wazuh-manager` and `/etc/wazuh-dashboard` (uninstalling a package may keep part of them). On the control node, remove `deployment-credentials/` and `deployment-config-files/`. The playbooks provide the credentials and the CA of a component only before its package is installed.

To add a node to a distributed deployment, add it to `instances` and run the playbook again: its certificates are issued from the CA of the deployment and staged before its package is installed. The certificates of the nodes already installed are kept as they are.

Running the playbook again with the same packages leaves them installed as they are and does not write `local.env` again. It downloads the packages and checks their signatures again, writes the Wazuh Indexer hosts of `wazuh-manager.conf` and `opensearch_dashboards.yml` again, and restarts the services.

### Upgrading

The playbooks are not an upgrade procedure. Between 5.x releases, upgrade each component as its documentation describes.

A Wazuh Manager 4.x cannot be upgraded in place to 5.0, and neither can a 5.0.0 RC 1 or earlier pre-release (wazuh/wazuh#40338). Deploy 5.0 on new hosts and carry the agent keys, the agent registry and groups, the enrollment password and the Wazuh server API users across with the manager migration procedure, [Migrating a Wazuh manager from 4.x to 5.0](https://github.com/wazuh/wazuh/blob/5.0.1/docs/guide/migration/manager-4x-to-5x.md), automated by [`wazuh-migrate-identity.py`](https://github.com/wazuh/wazuh/blob/5.0.1/tools/migration/wazuh-migrate-identity.py). The same guide covers the configuration, the ruleset and the agents.

## Post-Deployment Steps

After deployment, access the Wazuh Dashboard by navigating to `https://<WAZUH_DASHBOARD_IP_ADDRESS>` in your web browser. Log in as `admin`, with the password in `deployment-credentials/WAZUH_INDEXER_ADMIN_PASSWORD` on the control node:

```bash
  cat deployment-credentials/WAZUH_INDEXER_ADMIN_PASSWORD
```

### Change the passwords

The deployment playbooks do not rotate passwords. To change them, use the `wazuh-passwords-tool.sh` script of the [Wazuh installation assistant](https://github.com/wazuh/wazuh-installation-assistant), following its documentation. The tool only updates the host it runs on:

- **All-in-One.** Run `wazuh-passwords-tool.sh -a` on the host. It changes every password, updates the keystores and the credential files of the host, and restarts the services.
- **Distributed.**
  1. On a Wazuh Indexer node, run `wazuh-passwords-tool.sh -a`. It changes `admin`, `kibanaserver` and `wazuh-manager`.
  2. On the Wazuh Manager master node, run `wazuh-passwords-tool.sh -a`. It changes `wazuh` and `wazuh-internal-client`. These users live in the `rbac.db` of the master, which the cluster does not synchronize: a node promoted to master later keeps the passwords it was installed with, so change them again on it.
  3. On every Wazuh Manager node, write the new `WAZUH_INDEXER_MANAGER_PASSWORD` to the keystore (`wazuh-manager-keystore -f indexer -k password`) and to `/etc/wazuh-manager/local.env`, and restart `wazuh-manager`.
  4. On every Wazuh Dashboard node, write the new `WAZUH_INDEXER_KIBANASERVER_PASSWORD` (`opensearch.password`) and `WAZUH_MANAGER_WUI_PASSWORD` (`wazuh_core.hosts.default.password`) to the keystore and to `/etc/wazuh-dashboard/local.env`, and restart `wazuh-dashboard`. Write the keystore as root, then give it back to the service group:

     ```bash
     cd /
     printf '%s' '<new password>' | sudo OSD_PATH_CONF=/etc/wazuh-dashboard /usr/share/wazuh-dashboard/bin/opensearch-dashboards-keystore --allow-root add -f --stdin opensearch.password
     sudo chown root:wazuh-dashboard /etc/wazuh-dashboard/opensearch_dashboards.keystore
     sudo chmod 640 /etc/wazuh-dashboard/opensearch_dashboards.keystore
     ```

     Repeat the `printf` line with `wazuh_core.hosts.default.password` for the Wazuh server API password.

  The new values are in the `export/credentials.env` file of the node where the tool ran. The other nodes keep the previous values in their own `export/credentials.env`.

> **Note:** Change one user at a time, or use `-a`, and check that the tool finishes without errors before updating the other nodes. If it stops partway, the Wazuh Manager or Wazuh Dashboard keystore on that host may already hold a password that the Wazuh Indexer did not receive. See the documentation of the tool before running it again.

After changing the passwords, copy each new value to the file of its key in `deployment-credentials/` on the control node. All-in-One, the next run of the playbooks takes the published values and copies them there itself. In a distributed deployment, the health checks of the next run use `deployment-credentials/`, so a run before you copy them fails with the password rejected. A run that finds a published password that differs from `deployment-credentials/` prints a warning that names the key: after a password change, it is expected on the nodes where the tool did not run.
